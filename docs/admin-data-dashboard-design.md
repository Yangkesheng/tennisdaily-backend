# 管理员数据看板设计

## 1. 目标

为 TennisDay 管理员提供产品运营看板，观察每天新增用户、打球记录，以及用户新增球拍、穿线记录、球鞋的趋势，并识别用户是否持续使用产品。看板只服务于产品运营和产品改进，不作为用户排行榜或个人画像工具。

首期基于现有业务表聚合数据，不建立独立数仓，也不要求所有页面点击都上报埋点。现有管理员身份沿用 `admin.userIds` 配置和 `RequireAdmin` 中间件。

## 2. 看板信息架构

### 2.1 概览页

默认显示最近 30 天，支持 7 天、30 天、90 天和自定义日期范围。顶部指标卡：

| 指标 | 定义 |
|---|---|
| 新增用户 | `users.created_at` 落在所选自然日，且用户未软删除的去重用户数 |
| 新增打球记录 | `tennis_sessions.created_at` 落在所选自然日且 `deleted_at IS NULL` 的记录数 |
| 新增球拍 | `racket.created_at` 落在所选自然日且未软删除的球拍数 |
| 新增穿线记录 | `racket_stringing_record.created_at` 落在所选自然日且未软删除的穿线记录数 |
| 新增球鞋 | `my_shoes.created_at` 落在所选自然日且未软删除的球鞋数 |
| 活跃用户（DAU） | 在该自然日发生至少一个已保存业务行为的去重用户数，首期可由上述业务表当天新增数据推导；行为埋点上线后按事件口径补充 |

趋势图按天展示以上新增量。允许多选指标；默认展示用户、记录、球拍、穿线、球鞋五条曲线。DAU 单独显示或使用第二坐标轴，避免量级差异遮蔽趋势。

### 2.2 用户增长与留存

- 新增用户趋势：按用户创建日统计。
- 注册后首个关键行为转化：注册后 1/7 天内是否完成首次打球记录；后续可扩展首次新增球拍、球鞋。
- 留存：注册日 cohort 的第 1、7、30 日活跃率。仅在业务行为事件口径明确、数据覆盖完整后开放，避免把登录刷新或后台请求算作活跃。
- 活跃定义：至少一次成功保存/更新核心业务数据，或显式打开产品并产生经批准的行为事件。首期 MVP 可以只提供“有新增业务数据的用户数”并清楚标注，不将其误称完整 DAU。

### 2.3 业务行为

- 每日打球记录新增数、记录用户数、平均每活跃记录用户新增数。
- 每日新增球拍、球鞋、穿线记录数及对应去重用户数。
- 装备关联率：打球记录中 `racket_id` / `shoe_id` 有效关联的比例；需排除默认值 0，并说明统计分母为未删除打球记录。
- 球拍/球鞋首次添加后的后续使用：拥有装备用户中至少有一条打球记录引用该装备的比例。
- 穿线记录关联球拍完整度、费用填写率（如运营需要）。

### 2.4 行为漏斗（埋点阶段）

按匿名/内部 user ID 聚合，不显示敏感个人字段：

1. 小程序启动/进入首页
2. 打开新增打球记录
3. 成功保存打球记录
4. 打开装备页
5. 成功保存球拍 / 球鞋 / 穿线记录

漏斗按会话或 1 日窗口计算转化，并允许按版本、来源（若合法且可取得）分组。失败请求和页面点击只用于诊断，不计入业务成功转化。

## 3. 口径与时间规则

- 看板时区统一为 `Asia/Shanghai`，日范围使用左闭右开 `[00:00, 次日00:00)`。
- “新增”依据实体 `created_at`，而不是业务日期字段：打球记录使用创建时间而非用户填写的打球时间；穿线记录使用创建时间而非 `string_date`。这样衡量产品内新增行为，不会因补录历史而改变历史业务日期曲线。
- 更新已有记录不算“新增”。若以后需要衡量编辑行为，新增单独事件或审计数据。
- 软删除数据排除在当前有效数据量外。新增趋势建议保留“创建数”口径，即创建后又删除的对象仍属于发生过的创建行为；可另提供删除数/净增量，避免删除回滚历史增长。具体图表要标明口径。
- 注册以 `users.created_at` 为准；微信身份表绑定或登录请求不能重复计为新用户。
- 当前系统若曾物理删除，历史“净用户数”无法完整还原；看板需注明数据从可用时间起统计。
- 空数据日期补 0；自定义日期上限建议 366 天，超过时按周聚合。

## 4. 建议增加的行为埋点

首期不建议埋所有点击。优先采集以下能回答关键产品问题的行为：

| 事件 | 触发时机 | 用途 |
|---|---|---|
| `app_open` | 小程序前台启动/回到前台，采样或按日去重 | 粗略使用频率、DAU；需确认生命周期实现和去重策略 |
| `session_create_success` | 打球记录服务端创建成功 | 首次记录转化及保存成功率；也可由业务表推导 |
| `session_create_failure` | 保存请求失败后 | 定位记录流程失败，属性仅记录错误类别，不记录备注/请求体 |
| `racket_create_success` | 球拍创建成功 | 装备使用转化；也可由业务表推导 |
| `shoe_create_success` | 球鞋创建成功 | 球鞋使用转化；也可由业务表推导 |
| `stringing_create_success` | 穿线记录创建成功 | 穿线功能采用情况；也可由业务表推导 |
| `entry_open` | 打开首页核心入口（记录、球拍、球鞋、穿线） | 查看入口到保存之间的转化；只采核心入口，不全量页面浏览 |
| `onboarding_complete` | 用户完成首次引导（如果引导存在） | 新用户激活分析 |

业务创建成功事件若与业务表重复保存，应仅作为诊断和漏斗补充；权威新增量仍查询业务表。可由服务端在成功写入后记录，保证不会出现客户端误报。页面打开等前端事件才从客户端上报。

### 事件公共字段

- `eventName`、`eventTime`（服务端统一生成或校验）、`userId`（从 JWT 派生，不信任客户端传入）、`sessionId`（随机会话标识）、`appVersion`、`platform`、`schemaVersion`。
- 可选属性限定为白名单，如 `entry`、`category`、`durationBucket`、`errorCode`；禁止自由 JSON 大对象。
- 不采集微信 OpenID/UnionID、手机号、昵称、头像、备注文本、球场精确位置或完整错误堆栈。
- 事件写入失败不得阻断记录保存；后端关键成功事件优先与业务写入同事务，或通过可重试的轻量机制，MVP 可直接由业务表聚合。

## 5. 数据与实现建议

### 首期 MVP：业务表聚合

沿用现有表：`users`、`tennis_sessions`、`racket`、`racket_stringing_record`、`my_shoes`。新增管理员只读统计接口，服务层聚合，repository 层查询；路由放在现有受 `RequireAdmin` 保护的 `/api/admin` 下。接口响应遵守统一 `{code,message,data}` 格式，JSON 使用 camelCase。

建议接口：

- `GET /api/admin/analytics/overview?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD&granularity=day`
- `GET /api/admin/analytics/series?startDate=...&endDate=...&metrics=users,sessions,rackets,stringings,shoes,activeUsers`
- 后续视需要增加 `GET /api/admin/analytics/retention` 和 `GET /api/admin/analytics/funnel`。

概览响应包含查询范围、时区、指标口径版本和指标值；序列每个日期包含 `newUsers`、`newSessions`、`newRackets`、`newStringingRecords`、`newShoes`、`activeUsers`。不要返回原始用户明细或用户联系方式。

首期直接按日期范围聚合已有索引字段。数据量增长后再根据慢查询证据增加聚合日表；不先引入消息队列、Redis 或独立数仓。对包含日期字段和软删除条件的查询检查执行计划，必要时增加匹配索引。

### 埋点阶段

需要完整 DAU、留存、入口漏斗时，再增加受控事件表（例如 `analytics_events`）：事件 ID、用户 ID、事件名、发生时间、会话 ID、版本、平台、受限属性 JSON、创建时间。按 `(event_name, occurred_at)`、`(user_id, occurred_at)` 建索引；定义保留期限和聚合方式。避免把事件表当审计日志或存放任意用户内容。

## 6. 管理员界面与访问控制

- 入口仅在管理员授权后显示；前端入口隐藏只是体验控制，所有 `/api/admin/analytics/*` 请求必须由 `RequireAdmin` 校验。
- 页面区块：日期范围、指标卡、每日趋势、用户激活与留存、核心行为漏斗、数据更新时间/统计口径说明。
- 图表支持 hover 查看日期和数值；支持导出汇总 CSV（不含用户明细）作为后续项。
- API 返回查询区间和 `generatedAt`，异常时显示错误状态，不展示伪造的 0。
- 管理员身份继续沿用配置白名单；如未来需要角色与审计，再单独设计权限模型。

## 7. 隐私、安全与治理

- 统计遵循最小化原则，只呈现汇总指标；看板不需要 OpenID、手机号、昵称或用户级明细。
- 防止通过筛选组合反推出个体：未来若增加细分维度，低于 5 人的分组可隐藏或合并。
- 导出仅限汇总，不默认提供逐用户导出。
- 埋点在隐私政策中说明目的、字段和保留期；不得采集备注、精确位置、手机号等非必要内容。变更隐私告知或采集范围时按产品发布流程评估。
- 事件名和属性需版本化；每个指标在接口文档与看板提示中引用同一口径定义。

## 8. 分阶段落地

1. **MVP 数据看板**：管理员汇总接口与页面；日新增用户、打球记录、球拍、穿线记录、球鞋；范围筛选和趋势图；指标定义和软删除处理。
2. **活跃与激活**：确定 `app_open` 定义及小程序生命周期去重，建立关键行为漏斗；区分“业务新增用户数”和完整 DAU。
3. **留存与质量**：按注册 cohort 计算 1/7/30 日留存，观察首次记录转化、记录失败率、装备关联率。
4. **规模化优化**：依据慢查询和数据量决定日聚合表、缓存、导出与告警，不预设复杂基础设施。

## 9. 验收标准

- 仅管理员可以访问统计接口；普通登录用户得到统一 403 响应。
- 五类新增指标按 `Asia/Shanghai` 自然日正确统计，并区分创建时间与业务时间。
- 软删除规则在指标说明中明确；空日期补零，非法或过长日期范围返回参数错误。
- 接口只返回聚合数据，不含用户明细或敏感标识。
- 看板标明时间范围、时区、指标定义和数据更新时间。
- DAU/留存仅在定义和数据覆盖可验证后启用，不使用登录接口调用数冒充用户活跃。
